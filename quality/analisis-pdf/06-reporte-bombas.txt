FuelTech Master es un proyecto técnicamente inusual dentro de su rango: una aplicación web pensada
para un taller real de reparación de bombas de gasolina en Latinoamérica, escrita sin framework de build,
con 407 pruebas automáticas, 18 reglas anti-regresión estáticas, un sistema de "trinquete" de métricas que

2.1 Qué es FuelTech Master y para quién es
Antes de cualquier juicio técnico, hace falta entender qué es esto, porque el proyecto no puede leerse con
las mismas gafas que una SaaS B2B de市委. La pieza de identidad del propio repo, AGENTS.md , abre con una
definición sin romanticismo:
"FuelTech Master es la herramienta de consulta de un taller real de reparación de módulos y pilas (bombas) de
gasolina en Latinoamérica. Un mecánico la abre en el celular, con las manos sucias, para decidir si una bomba
sirve o se devuelve. Si publicas una presión equivocada, alguien cambia una pieza buena o deja una mala puesta.
Por eso este proyecto es estricto." ( AGENTS.md:12-18 )
De ahí derivan todas las decisiones que en otro proyecto se leerían como excesos pedantes, y aquí son
obligaciones:
Vocabulario del dueño, no vocabulario del libro: el proyecto usa "pila" (la bomba sola, en bruto),
"módulo" (el ensamble), "riel/flauta" (el conducto) y "banco" (la prueba deadhead). Cambiar el
vocabulario por uno técnico "más correcto" rompería al usuario objetivo (heurística 2 de Nielsen: match
between the system and the real world).
La regla de 90 PSI: en un sistema Vortec/CSFI, "con menos de 60 PSI en el riel los poppets no abren y el
motor no enciende". Esa única frase aparece en AGENTS.md:131 , lib/domain.js:pumpsForClass y las
pruebas de test/unit/domain.test.js , y cerrado por una regla del guard ( no-inventar-datos ).
Cambiar el número sin fuente es, en este contexto, dañar a un cliente.
Familia Yaris (Toyota: Yaris, Corolla, Corolla GR-S, Avanza, plataformas 1NZ/2NZ/ 1ZZ/2ZR-FE): 38/44 PSI
en vez de 50/60 PSI para MFI genérico ( lib/domain.js:133-137 ). Es la única excepción a la regla MFI, y
es la excepción porque viene de un manual, no de una estimación. Sale hasta en el JSON-LD de
index.html .
Quien no lea AGENTS.md antes de tocar una línea no puede trabajar en este proyecto: ahí está el "contrato
de trabajo". El equipo中人, lo dice literal: "No es documentación opcional: casi todo lo que dice está
respaldado por una prueba o por una regla de scripts/guard.js que va a fallar si lo ignas."

3. Arquitectura y Clean Architecture
El mencionado esquema de Robert C. Martin en Clean Architecture: A Craftsman's Guide to Software Structure
and Design (Pearson, 2018) propone el principio rector de "la dependencia debe apuntar hacia las capas
internas": el dominio (las reglas del negocio) no depende de nada externo — ni base de datos, ni web, ni
framework. La pregunta decisiva de este capítulo es: ¿puedo probar las reglas del negocio sin levantar la
base de datos, sin un cliente HTTP y sin React? En FuelTech Master la respuesta es sí, y eso es lo que
distingue un proyecto limpio de un proyecto "que funciona".
3.1 Capas y Ley de Dependencias
El proyecto se organiza en cuatro anillos conceptualmente limpios:
┌────────────────────────────────┐
│ public/ ← UI (React + htm) │ ← externo
│ no build step │
├────────────────────────────────┤
│ server-pg.js ← API / SSR │ ← adaptadores I/O
│ db.js ← adaptador DB │
├────────────────────────────────┤
│ lib/pure.js ← helpers puros │ ← utilidades
├────────────────────────────────┤
│ lib/domain.js ← REGLAS │ ← dominio
│ lib/catalog.js ← DATOS │
└────────────────────────────────┘
flecha de dependencia ───► hacia dentro
El dominio ( lib/domain.js ) depende de los datos ( lib/catalog.js ) pero no al revés. El catálogo
exportaba constantes y el dominio las consume; el catálogo no importa nada del dominio. Es el
comportamiento esperado de una capa de datos.
Los adaptadores ( db.js , server-pg.js ) dependen del dominio. db.js no conoce las reglas del
taller; el servidor sí las consulta a través de require('./lib/domain') .
La UI ( public/app.js , public/microapps.js ) habla con la API por HTTP; no conoce la base de
datos, ni las reglas del taller, ni siquiera lib/domain.js . En microapps.js se ven importaciones del
catálogo y helpers para⚜ar DTC; son réplicas de datos públicos, no un atajo de capas.
3.1.1 La pureza de lib/ está protegida por una regla del guard
No basta con diseñar la pureza; hay que defenderla. El proyecto incluye una regla del guard
(destructiva, no advisory) que aborta el build si lib/ toca lo que no debe:
/* scripts/guard.js — regla lib-es-puro */
revisar() {
// qué busca: require('./db'), express, process.env, console.log
// dentro de cualquier archivo de lib/*.js.
// falla el build si encuentra uno.
}

3.2 Separación de responsabilidades (SRP en la práctica)

tocan? Respuesta, según el propio repo: exactamente tres, todos juntos en el mismo commit, y
mandatorio: cambio en lib/domain.js + cambio en la prueba + fuente del dato en el mensaje de
commit.

La función moduleProfile({…}) en lib/domain.js:42-122 define un objeto P con cinco tipos
de ensamble ( external , hanger_tbi , hanger_return , module_returnless , vortec , gdi_low ).
Añadir un nuevo tipo de ensamble no requiere cambiar la función: basta añadir una entrada al
diccionario P y una rama al switch del assembly . Es OCP en JavaScript puro, sin abstracciones.
El inverso, también OCP: la regla de presión de riel para MFI está protegida contra modificación
accidental. En railPressure({brand, model, inj, psiMin, psiMax}) ( lib/domain.js:133-137 ):

if (inj !== 'MFI') return { min: psiMin, max: psiMax };
if (esFamiliaYaris(brand, model)) return { min: 38, max: 44 };

{@code railPressure} nunca lee los psiMin / psiMax del catálogo cuando la inyección es MFI: aplica la
regla de taller. Sobre el subconjunto MFI, la regla es cerrada a modificación por datos. Sin esto, una
fila del catálogo con psiMin=40, psiMax=45 para un MFI genérico pasaba a producción y un mecánico
recibía 40-45 en la ficha aunque el banco real del taller esperara 50-60. Es OCP por codificación de la
regla: la regla no se puede romper agregando filas al catálogo.

3.5 ISP y LSP — observaciones
ISP (Interface Segregation): db.js expone sólo lo que el servidor usa: get , all , run , exec ,
insertReturningId , prepare . No obliga a los handlers a "saber" si están en Turso o en PostgreSQL.
El modificador mode = 'auto' | 'local' | 'turso' | 'pg' permite a las pruebas inyectar 'local'
sin tocar los handlers. Es ISP: el cliente pide lo que usa, no más.
LSP (Liskov Substitution): el proyecto no tiene herencia de clases, así que el chequeo clásico de LSP no
aplica directamente. Pero hay un sabor de LSP en que el contrato del adaptador es idéntico entre
backends: await db.get(sql, params) → fila | null en todos los casos. Si el desarrollador de
PostgreSQL rompiera el contrato (p. ej. devolviendo un array en vez de una fila), el resto del código
haría un .value sobre un array y fallaría, igual que con SQLite. El contrato es la abstracción que
debe respetarse, no la implementación.

4. Código limpio, SOLID y Boy Scout Rule
El capítulo 1 de Clean Code ("Clean Code", R. C. Martin, Prentice Hall, 2008) abre con una cita de Ron
Jeffries: "no deja el campo de campamento más limpio de lo que lo encontraste" — el Boy Scout Rule.
Existe una marca de cumplimento en este proyecto: el campo de campamento se mide con npm run
metrics , se persiste en quality/baseline.json y el build falla si empeora. El trinquete es esa regla.
4.1 Nombres, tamaño de funciones y comentarios
Nombres
La regla de Martin: "un nombre debe revelar intención". En todo el repo, los nombres tienden a ser
descriptivos y no a esconder nada:

no debería necesitar un comentario.
Tamaño de funciones
La recomendación de Clean Code ("no más de 20 líneas",Chapter 3: Functions) no la cumple siempre

El commit de 2026-08-11 con la creación de lib/pure.js es una refactorización activa de DRY: el

continuo (reglas del tipo pure-helpers-unicos ) que se ejecuta después de cada edición. Es el
Boy Scout Rule automatizado: el cambio que rompe la unicidad del helper aborta el build antes
de que alguien lo llegue a usar.

KISS (Keep It Simple, Stupid)
Decisiones arquitectónicas deliberadamente "aburridas":
Sin build step: el frontend no necesita npm install en producción, no se rompe el despliegue al

Casos de YAGNI se ven en negaciones explícitas:
No hay cache en el cliente ahand; el service worker ( public/sw.js ) tiene 2,2 KB y cachea los

No hay i18n: el usuario es hispanohablante, tiene razón; duplicar el bundle con un runtime i18n

No hay panel de control drowning\nadmin olaboratorio. El admin está desactivado (503) si no hay

4.3 Tratamiento de errores y nulidad
Clean Code dedica capítulos a "Don't Return Null" y "Don't Pass Null". El proyecto los superado sal
con una solución pragmática en JavaScript, donde null es inevitable: los helpers puros normalizan
las entradas, no las pushean al backend. El ejemplo más representativo es toInt en
lib/pure.js:16-19 :
const toInt = (v, min, max) => {
const n = Number.parseInt(v, 10);
return Number.isSafeInteger(n) ? Math.min(Math.max(n, min), max) : null;
};
El uso en handlers ( server-pg.js ):
const id = toInt(req.params.id, 1, 1e9);
if (id === null) return res.status(404).json({ error: 'No encontrado' });

que ya ocurrió en este proyecto. Cada helper de pure.js tiene el mismo patrón: una historia del

CUMPLE FUERTE

6.1 A01:2021 — Broken Access Control
El riesgo de control de acceso mal aplicado es el #1 desde OWASP 2021. En FuelTech Master el
núcleo del riesgo es multi-tenant: talleres distintos comparten tablas y cualquier consulta
sin WHERE workshop_id = ? es una fuga de datos entre negocios. El proyecto resuelve esto con
una solución que es, por mucho, lo mejor del código:
La regla de oro documentada en AGENTS.md:211-213
"Los talleres comparten tablas. Una consulta sin ese filtro es una fuga de datos entre
negocios. Va en todas: SELECT, UPDATE y DELETE, aunque ya hayas comprobado la propiedad
antes." Es decir: el filtro se aplica incluso cuando el handler ya validó la
pertenencia, porque es defensa en profundidad.
El robot test/robots/aislamiento.js implementa una verificación que es la prueba real:
recorre todas las rutas protegidas de server-pg.js y las ataca una por una desde una cuenta
ajena. Es un fuzz dirigido, no un test de casos felices. El resultado de la última corrida
( quality/ROBOTS.md:12 ):

Test qa/security.test.js contiene IDOR checks explícitos: "el taller B no puede BORRAR un
registro del taller A conociendo su id", "el taller B no puede MODIFICAR inventario del

Prueba security.test.js:141 : cookies HttpOnly y SameSite ; security.test.js:162 : el

const salt = crypto.randomBytes(16);
const hash = crypto.scryptSync(pass, salt, 64);
return

function verifyPassword(pass, stored) {
const parts = stored.split('$');
if (parts[0] !== 'scrypt' || parts.length !== 6) return false;
const N = parseInt(parts[1], 16); const r = parseInt(parts[2], 16); const p =
parseInt(parts[3], 16);
const salt = Buffer.from(parts[4], 'base64');

El problema: crypto.scryptSync es la variante síncrona de scrypt. Ocupa el event loop entero

producción), cada cálculo dura ~115 ms de CPU bloqueada. Es la solución algorítmica correcta
(scrypt con parámetros correctos, sal aleatoria embebida en el hash, comparación de tiempo
constante timingSafeEqual , sal en bytes aleatorios con randomBytes(16) ), pero su forma
técnica es dañina para el event loop.
Evidencia del propio robot de registro ( quality/ROBOTS.md:24-28 ):
Reposo del bucle de eventos: p50 11,1 ms · p95 11,8 ms · máx 13 ms .
Con 8 altas concurrentes: p50 10,8 ms · p95 12 ms · máx 818,5 ms .
El matrimonio estás en la matemática: 8 altas × 115 ms de CPU síncrono = 920 ms de bloqueo
del event loop; en la medición llegó a 818,5 ms ( ROBOTS.md:27 ).
Una consulta del catálogo, durante alta concurrente: máx 668,6 ms .

Impacto
El bloqueo del event loop no es простelo por la paginación. Cualquier otra petición del
servidor — /healthz , API, servicio de catálogo, página SSR — se cuelga mientras se
procesa el scrypt. Con 8 usuarios en alta simultáneas el sistema ofrece un "tiempo de

p95 extremo; no es una simple demora, es una denegación de servicio accidental.
Solución: sustituir crypto.scryptSync por crypto.scrypt (asíncrona, basada en
callbacks/Promises). El propio robot lo postula:
async function hashPassword(pass) {
const salt = crypto.randomBytes(16);
return new Promise((resolve, reject) => {
crypto.scrypt(pass, salt, 64, { N: 16384, r: 8, p: 1 }, (err, hash) => {
if (err) return reject(err);
resolve(`scrypt$${16384}$${8}$${1}$${salt.toString('base64')}$${hash.toString('base64')}
`);
});
});
}
Toda llamada actual ( server-pg.js:1695 y 1710 ) ya está dentro de un handler async, así que
el await funciona directo. Es un cambio de una sola línea y de un orden de magnitud menor en
impacto: el código resultante es compatible con la estructura actual, explosiona el
throughput y elimina el bloqueo del event loop. Es la primera recomendación de la sección 12
(roadmap).
6.3 A03:2021 — Injection
El riesgo de inyección (SQL, NoSQL, OS, LDAP) es el más probable en cualquier backend común.
En FuelTech Master el riesgo está controlado por cinco prácticas:
1. Queries parametrizadas en todo el código: todos los handlers usan db.run(sql, [params])
con ? ; el adaptador traduce a $1, $2, … en PostgreSQL. No hay concatenación manual. El
guard db-params-en-array refuerza el uso de array en vez de argumentos sueltos (ya
corregido bug antes de que se detectara).
2. Validación de entradas numéricas: toInt(req.params.id, 1, 1e9) y if (id === null) return
res.status(404).json({ error: 'No encontrado' }) . Los ids llegan a la base como enteros,
no como strings.
3. Escape de HTML en SSR: esc() de lib/pure.js escapa & < > " ' . El propio AGENTS.md:218-
220 es claro: "No escribas otra función de escape. Dos escapes que se separan son un XSS
esperando." Es DRY forzado por el guard.
4. CSP estricta con nonce por petición: server-pg.js:188-218 usa
helmet.contentSecurityPolicy con default-src 'self' y nonce por petición para scripts
inline. Los hashes de CSP de los scripts inline de index.html se calculan del archivo
real, no se pegan a mano ( server-pg.js:175-186 ),正常izando CRLF→LF porque el proyecto se

el servidor se entere." Es CSP حب rigurosidad.

12.4 Lo que NO hay que tocar
El proyecto tiene decisiones deliberadas que no deben cambiarse aunque un auditor "normal" lo
solicitaría. Respetarlas es tanto parte del proceso de auditoría como las recomendaciones:
lib/domain.js debe seguir puro: sin require('./db') , sin process.env , sin
console.log . El guard lo defiende. Tocar esto rompe el tiempo de prueba (ltima de 1 ms) y
el compromiso de cobertura 100 %.
El vocabulario del taller: "pila", "módulo", "riel/flauta", "banco", "familia Yaris". No
se "moderniza" con jerga académica. El usuario objetivo lo necesita así.
verified = 0 por defecto: no se inventan datos técnicos sin fuente. Es la honestidad con
el mecánico.
El trinquete y el máximo 5 en known-issues.json : el techo obliga a resolver antes de
agregar. Subir el tope es hacer trampa.
El handler async envuelto ( const envolver ): Express 4 lo necesita. Migrar a Express 5
(que captura promesas rechazadas automáticamente) es válido, pero hasta entonces el
envoltorio es lo que evita peticiones colgadas.
El payload del db.run(sql, [params]) en array: el guard lo defiende, y los bugs ocurrido
dee dañar toy.
Sin ORM: cada handler escribe el SQL exacto que necesita. Un ORM oculta el dialecto y
desplaza los problemas al adaptador del ORM, no del motor.
Sin build step en producción: es el presupuesto de tamaño y la velocidad de despliegue.
TypeScript en lib/ es compatible (ver #15) siempre que el target sea ESM sin transpiler.
Cierre
FuelTech Master es un proyecto que aplica principios de Clean Code, SOLID, WCAG, Nielsen
y OWASP no por cumplir normas, sino porque son la forma correcta de defender el trabajo
real de un taller de bombas de gasolina. La deuda que tiene está visible y acotada, las
pruebas la cubren y los robots la miden. La única acción urgente es sustituir
scryptSync por scrypt ; las demás son mejoras de escala y DX. El campo de campamento
está más limpio de lo que lo encontramos; este reporte es agradecerlo y ayudar a la
siguiente revisión.
