1. Resumen ejecutivo
FuelTech Master es la herramienta de consulta de un taller real de reparación de módulos y pilas (bombas) de gasolina en Latinoamérica: el
mecánico la abre en el celular, con las manos sucias, para decidir si una bomba sirve o se devuelve. Ese contexto de «malentendido fatal» (una
presión equivocada = cambiar una pieza buena o dejar una mala puesta) domina todas las decisiones de ingeniería del proyecto y explica por qué
tiene una disciplina de calidad que supera al 95 % de los proyectos de su tamaño.
1.1 Lo que está excepcional
Contrato de trabajo vivo: AGENTS.md (335 líneas) documenta el vocabulario del dominio (pila/módulo/riel/banco), las reglas del taller, las
trampas que ya ocurrieron y los límites de seguridad. Casi todo está respaldado por una prueba o por una regla de scripts/guard.js.
Calidad medida, no declarada: 407/407 pruebas en ~7 s, cobertura 100 % de lib/, 79 rutas de API (100 % probadas), 18 reglas de restricción
con 0 violaciones, presupuestos con trinquete quality/baseline.json (mejorar libre; empeorar falla el build).
Robots de prueba masiva: 7 robots con Puppeteer (~5 050 comprobaciones en 321 s): aislamiento entre talleres, fuzz de ~2 900 cargas
hostiles sin un solo 500, recorrido SEO del sitemap, jornada real con navegador y un robot interfaz que mide contraste (componiendo alphas),
desbordes, scroll anidado y objetivos táctiles en 2 temas × 3 anchos — 214/214 en verde.
Seguridad por defecto: CSP con nonce por petición y hashes calculados del archivo servido (server-pg.js:143,175), HSTS preload, rate-limit
por capas, comparación de secretos en tiempo constante (server-pg.js:50,1368), aislamiento por workshop_id en toda consulta, y un wrapper
envolver que arregla la falta de captura de promesas rechazadas de Express 4 (server-pg.js:124-139).
UX de altísima calidad en el catálogo: sistema de color semántico de 3 roles (lima=confirmado, ámbar=aviso, rojo=falla real), contraste
calibrado en navegador, esqueleto SSR que elimina la pantalla en blanco, estados vacío/error/loading distinguidos, y PWA instalable con icono
maskable y estrategia network-first.

4. Auditoría Clean Code — Backend
Marco: Robert C. Martin, Clean Code (2008). Se evalúan nombres, funciones, comentarios, formato, errores, DRY, SOLID y estructura. El veredicto es
doble: el código dentro de las funciones es, en general, limpio, honesto y autoconsciente (los comentarios explican por qué, no qué); el problema es
estructural — un solo archivo lo contiene casi todo.
4.1 El god-file: server-pg.js (2 662 líneas, 181 343 bytes)
Hallazgo estructural principal. Un único archivo mezcla: configuración y variables de entorno (13-51), migraciones de esquema (78-97),
wrapper de promesas (124-139), CSP/helmet/rate-limit (188-235), plantillas SSR y contenido SEO (279-933), el panel de administración (1352-
1582), la API de talleres (1635-2581), el chat de IA (1253-1347), el envío de email (1877-1923), el marketplace «connect» (2363-2397), el
backup/restore con SQL dinámico (2476-2521) y el arranque del proceso (2616-2657).
Contraste con Clean Code: «Clases» (cap. 10) y «Sistemas» (cap. 11) piden una sola responsabilidad por módulo, cohesión alta y dependencias
explícitas. Aquí la única «clase» es createApp() con 79 handlers como cierre. Consecuencias medibles:
Acoplamiento: un cambio en el formato de error toca un archivo de 2 662 líneas; la revisión por diff es imposible de aislar por dominio.
Topes estructurales ya alcanzados: quality/budgets.json fija max_lineas_por_archivo: 3000 y server-pg.js: 200 KB — hoy está en 177.1
KB. El límite no es adorno: el proyecto sabe que es un god-file y le puso presupuesto en vez de dividirlo.
Estrategia de salida recomendada (cap. 12): extraer routes/ por dominio, middleware/ (requireWorkshop, requireAdmin, limitadores),
services/ (gemini, correo, backup) y seed-context. Cada extracción debe caer dentro de la misma ruta para no romper el contrato de
pruebas (100 % de rutas probadas).
4.2 Lo ejemplar: patrones que cualquier proyecto debería copiar
a) El wrapper envolver (Express 4 + async) — server-pg.js:124-139
const envolver = (fn) => {
if (typeof fn !== 'function' || fn.length === 4) return fn; // no envuelve error handlers
const envuelto = (req, res, next) => {
let r;
try { r = fn(req, res, next); } catch (e) { return next(e); }
if (r && typeof r.then === 'function') r.catch(next);
return r;
};
return envuelto;
};
// monkey-patch de app.get/post/put/... para auto-envolver todos los handlers
Express 4 no captura promesas rechazadas: sin esto, un error en una ruta async deja la petición colgada para siempre. El comentario documenta el
bug real (GET /api/modules/abc no respondía nunca). Además preserva el nombre de la función para stack traces. Decisión técnica correcta,
explicada con evidencia — exactamente lo que pide Clean Code sobre comentarios.
b) Hashes CSP calculados del archivo servido — server-pg.js:175-186
Los hashes SHA-256 de los <script> inline de index.html se calculan leyendo el archivo real y normalizando CRLF→LF (el proyecto se edita en
Windows). Un hash pegado a mano «caduca en silencio» y el navegador bloquea el script sin aviso. Esto es DRY + defensa en profundidad: una
sola fuente de verdad.
c) Comparaciones de secretos en tiempo constante — server-pg.js:50, 1368-1369
const ok = a.length === b.length && crypto.timingSafeEqual(a, b);
Tokens de administración firmados con HMAC-SHA256 y expiración (39-51); contraseña de admin comparada con timingSafeEqual; contraseñas de
talleres con scrypt y salt (1635-1655). Prácticas de seguridad sin atajos.
d) Aislamiento por arrendatario — filtro workshop_id en todas las consultas
El contrato AGENTS.md §4.5 exige el filtro en SELECT/UPDATE/DELETE «aunque ya hayas comprobado la propiedad antes», y el robot aislamiento
(139 comprobaciones) ataca todas las rutas protegidas desde una cuenta ajena: 0 fugas. Nivel de disciplina poco común.
